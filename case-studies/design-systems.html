Angular design system

Creating scalable, usable, trusted design components and tokens.

Roles
Lead Product Designer, UX Engineer
Tools
Figma, Storybook, Angular, HTML, CSS
Team
All designers, all front-end developers
Timeline
Ongoing

Overview

Sourcescrub sought a visual upgrade from their Angular Material 14 components—wanting to achieve a more desirable app with more consistency across designs and development.

Goal

The primary objective was to create a library of components in Figma and in Storybook for ease of use by designers and developers.

Approach

Sourcescrub’s previous designer had begun to prepare a design library which followed an Atomic design structure (Atoms, Molecules, Organisms, Templates), and after discussion with the Product team leaders, I determined that it was best to continue that structure. This would allow us to communicate the differences between interactions and styles, as well as the perceived roles between micro interactions, such as buttons, and the larger interactions present in templates.

Design

In Figma, I began by creating a page for each type of Figma component or style. This simple structure would allow designers and developers who understand Atomic design a starting place for manually discovering components.

Each individual type of style or component gets its own section with documentation briefly describing what it is and how it’s used. Components which have flexible content have “swappers” or slots, depending on if the contents require a fixed style or not.

While building each component, I referred to the Angular Material documentation to understand the various available inputs and outputs, and reflected those in Figma whenever possible.

Our section on selects (styled ng-select or mat-button/mat-menu components). To aid designers, a “swapper” component is created for chips, allowing designers to easily mockup multi-select components.

Buttons – Variants, sizes, and states

Chips – Selection, filtering, and remove states

Form inputs – Labels, prefixes, and validation

Menus – Dropdown options and nested actions

Developer specifications

I also label properties for developers, so that they understand if a component property is for Figma only, content projection, or a component input value.

This clear mapping bridges the gap between design component properties and Angular input/output decorators, drastically reducing ambiguity during sprint handoffs.

Figma component properties with type labels for engineering handoff.

Interactive prototypes

Complex components, with full prototypes can be easily assembled from the design library components, like this prototype of a filter panel.

Because base molecules are already linked with realistic interaction states, assembling high-fidelity flows requires minimal overhead and guarantees production accuracy.

A filter panel prototype built in Figma using library components.

The “Molecules” available for designers.

Tokens

It was also important for designers to have control over the styles used in the components, and so I worked with the Director of our Client Engineering teams to devise a way to convert SVG files into Sass and CSS variables, which can be directly added to component library override properties.

These tokens loosely follow Material 3 token conventions:

  • Reference tokens for base color palettes and other small values (similar in use to CSS variables)
  • System tokens for styles, spacing, sizing, and role-based color assignments (similar in use to CSS properties)
  • Component tokens for combinations of system tokens, specific to a single component (similar in use to CSS classes)

Design tokens are created and managed in Figma’s Variables settings, using a plugin to convert to a useable JSON file.

Design tokens created and managed in Figma’s Variables settings, exported to JSON.

Storybook

After the initial version of the design library was complete, we created a Storybook instance so that we could host the components on Chromatic.

I and our entire front-end developer team created stories for every style and component in every state that we wanted to maintain and test. Chromatic allows us to capture UI changes with each code update, preventing errors—so long as a “story” exists for it.

At the start, most of the stories were simply restyled Angular Material components, but since the initial launch, I’ve added more and more custom Angular components, which better meet the team’s needs visually, and are more flexible and stable.

Sourcescrub’s Storybook library hosted on Chromatic.

Figma to Chromatic handoff

Once components are added to Storybook the link to Chromatic can be copied into the documentation of a component, which is immediately available to developers when they’re examining a project.

For complex components, these links can be added to individual variants to reduce confusion.

An example of a Chromatic link added to a button component.

“Since launch, all components in Sourcescrub’s designs are 100% traceable to a Design system component or a set of components.”

Learnings

Actual full implementation of the design system is an ongoing process. Legacy code takes time to update and it takes time to train developers on the UI-kit in Storybook and to break the habit of rebuilding things from scratch.

Next steps

As new code replaces old, it’s vital for designers to ensure that developers are using the UI-kit for new code, and that designers ensure that they themselves are using the design library.
